# python-dateutil (pulled in by botocore, a boto3 dependency) unconditionally
# does `import six` / `from six.moves import _thread` in dateutil/tz/tz.py —
# still true even in current dateutil, so pinning dateutil's own version (an
# earlier, wrong fix) does nothing. The actual bug is in `six` itself:
# `six`'s `_SixMetaPathImporter` (on sys.meta_path) only got a proper
# find_spec() in six 1.16.0 (2021, also six's final release) — importlib's
# module-repr machinery on Python 3.10+ expects that, and PySide6's own
# shibokensupport import hook (which runs inspect.getsource() on every
# newly-imported module to detect old/new-style signal usage) is what
# actually triggers building that repr for six.moves. Without this pin, an
# older `six` already sitting in site-packages (e.g. from an earlier partial
# install) never gets upgraded — nothing else in this dependency chain
# requires >=1.16.0, so pip has no reason to touch an already-"satisfying"
# older six — and every launch crashes with
# "AttributeError: '_SixMetaPathImporter' object has no attribute '_path'"
# a few imports into core/vcs/cloud_sync.py's `import boto3`.
six>=1.16.0
